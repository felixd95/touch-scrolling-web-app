\chapter{System Description}

\section{Apparatus}

\subsection{Web Application and AWS Setup}

The experimental system consists of a \textbf{React} single-page web application backed by a fully managed, event-driven AWS backend. All infrastructure is defined declaratively as code with \textbf{Terraform} and deployed through a \textbf{GitHub Actions} CI/CD pipeline. On every push to the main branch, the pipeline authenticates against AWS via OpenID Connect (OIDC, i.e.\ without long-lived static credentials), runs \texttt{terraform apply} to reconcile the AWS infrastructure with its version-controlled definition, and then builds and publishes the React frontend. The static frontend build artifacts are hosted in an \textbf{Amazon S3} bucket and served to participants through an \textbf{Amazon CloudFront} content-delivery distribution, which also terminates HTTPS.

The application backend is built around \textbf{AWS AppSync}, a managed GraphQL API service, which exposes queries and mutations for participant management (\texttt{createParticipant}, \texttt{updateParticipant}), for storing completed trial blocks (\texttt{appendParticipantAttemptBlock}), and for requesting a new transfer-function parameter set (\texttt{triggerNextParameterSet}). \textbf{Amazon DynamoDB} serves as the persistent, schemaless data store behind this API: each participant is represented as a single item holding demographic fields (name, e-mail, birth date, smartphone ownership, daily screen time), the currently active transfer-function parameter set, the next (candidate) parameter set once available, and the complete history of completed trial blocks stored as a nested JSON (\texttt{AWSJSON}) attribute.

Rather than being triggered indirectly through DynamoDB Streams, the machine-learning backend is invoked synchronously as part of the GraphQL request flow: whenever a participant finishes a block of 10 trials, the frontend calls the \texttt{triggerNextParameterSet} mutation, whose AppSync resolver invokes an \textbf{AWS Lambda} function. This Lambda function reads the calling participant's full trial history from DynamoDB, additionally performs a table scan to collect the (anonymized) trial histories of \emph{all other} participants recorded so far, and forwards both as a single JSON payload to an \textbf{Amazon SageMaker} inference endpoint. SageMaker is configured as a \emph{serverless} endpoint (rather than an always-on instance) with a maximum concurrency of 1 and 3072\,MB of memory, so that compute resources -- and cost -- are only allocated for the brief duration of an actual invocation instead of running continuously between experimental sessions. The endpoint executes a custom inference container based on an AWS Deep Learning Container image with a \textbf{BoTorch}/\textbf{GPyTorch} multi-task Gaussian Process (GP) implementation (Section~\ref{sec:ml-model} describes the model in detail). The parameter set produced by the model is returned to the Lambda function, written back into DynamoDB as the participant's \texttt{nextParameterSet}, and subsequently retrieved by the frontend once the participant confirms that they are ready to continue with the next block of trials.

This architecture is therefore event-driven end to end: raw interaction data are recorded by the frontend, persisted in DynamoDB in blocks of ten trials, evaluated on demand by the Gaussian-Process-based optimizer running on SageMaker, and the resulting new transfer-function parameters are made available to the participant for the subsequent block. This provides a clear separation between the presentation layer (React), the persistence layer (AppSync/DynamoDB), and the optimization logic (Lambda/SageMaker), while keeping every part of the system independently deployable and version-controlled through Terraform.

In addition to the cloud infrastructure, the transfer-function logic itself was derived from the Android platform source code. In particular, the implementation of Android's \texttt{OverScroller} class was analyzed in order to extract the mathematical behavior of its spline-based fling deceleration model and reimplement it as a parameterized, physically motivated transfer function for the web-based experimental system (see Section~\ref{sec:transfer-function}).

\subsection{Implementation Details}

\paragraph{List and scroll container.} The user interface presents a single continuously scrollable list of $N = 330$ entries, numbered consecutively. The list is not paginated in the sense of discrete page breaks or page-navigation controls; instead, the height of each list entry is computed dynamically from the available viewport height so that exactly 15 entries are visible within the scroll container at any given time. This keeps the spatial density of the list, and therefore the visual arrangement participants perceive, consistent across devices and across trials. The list itself is rendered inside a dedicated scroll container whose content is not scrolled using the browser's native scrolling behavior, but is instead translated vertically (via a CSS \texttt{transform: translateY()}) under full programmatic control of the custom touch-input pipeline described below.

\paragraph{Custom touch-input pipeline.} The frontend is implemented in \textbf{React} using plain \textbf{JavaScript}. To gain full control over the scrolling dynamics, the browser's and React's default scrolling behavior is disabled for the list container, and replaced by a custom pipeline that processes the native \texttt{onTouchStart}, \texttt{onTouchMove}, \texttt{onTouchEnd}, and \texttt{onTouchCancel} events directly. During a touch gesture, every incoming touch-move sample is time-stamped and appended to a rolling buffer (capped at a $100$\,ms time window and at most 20 samples). From this buffer, an instantaneous, exponentially smoothed velocity ($0.8\times$ previous $+\ 0.2\times$ instantaneous) is maintained for real-time drag feedback, while at the end of a gesture a linear-regression estimate of the finger velocity is computed from the buffered position/time samples, which is more robust to jitter than a simple two-point derivative. If this regression-based velocity exceeds a fixed fling threshold, it is passed into the fling/momentum model described in the next paragraph; otherwise the list simply stops at its current position (after being clamped back into the valid scroll bounds if the participant had dragged past the list's edges).

\paragraph{Transfer function.}
\label{sec:transfer-function}
The transfer function governing post-touch (fling) motion was implemented as a physically motivated model directly derived from Android's \texttt{OverScroller} spline-deceleration algorithm, rather than relying on the browser's native momentum scrolling or React Native's default scroll-view behavior. The implementation numerically reconstructs Android's normalized position/time lookup spline (100 samples, built from cubic-Bezier control points parameterized by an inflexion factor and by fixed start/end tension constants of $0.5$ and $1.0$) and uses it, together with a physically derived deceleration model, to compute the total fling distance and duration from the measured launch velocity. Six parameters directly shape this motion profile and constitute the search space of the optimization process described in Section~\ref{sec:ml-model}:

\begin{itemize}
  \item \texttt{scrollFriction} -- a dimensionless drag coefficient that scales both the fling distance and duration; larger values increase braking and shorten the fling.
  \item \texttt{x1}, \texttt{x2} -- together define the deceleration rate through the logarithmic relation $\ln(x1)/\ln(x2)$ (mirroring Android's fixed constant $\ln(0.78)/\ln(0.9)$), which shapes how strongly the motion decelerates over the course of the fling.
  \item \texttt{inflexion} -- the position (in $[0,1]$) at which the spline transitions from the initial high-speed phase into the stronger deceleration phase.
  \item \texttt{physicalCoeffTuning} -- a tuning multiplier on the physical coefficient that converts the launch velocity (in device-independent pixels per millisecond) into fling distance and duration; this coefficient is otherwise derived from Earth's gravitational acceleration ($9.80665\,\mathrm{m/s^2}$), an assumed screen density of $160\,\mathrm{ppi}\times$ device-pixel-ratio, and a unit-conversion constant of $39.37$.
  \item \texttt{maxLaunchVelocityPxMs} -- an upper bound (in px/ms) clamped onto the regression-estimated finger velocity before it is used to launch a fling, preventing unrealistically fast motion caused by noisy touch samples.
\end{itemize}

Overscrolling beyond the top or bottom of the list is permitted up to a fixed maximum overscroll distance of 120\,px and is visually compressed by a fixed resistance factor of $0.35$ (i.e.\ only 35\,\% of the overflow is translated into visible motion), independent of the six optimized parameters. Each of the six parameters above is additionally constrained to a fixed, predefined lower and upper bound (Table~\ref{tab:param-bounds}) which was chosen so that all transfer functions generated during the optimization process remain physically plausible and usable within the experimental setting; these bounds are shared verbatim between the frontend physics implementation and the optimization backend (Section~\ref{sec:ml-model}).

\paragraph{Machine-learning-based parameter generation.}
\label{sec:ml-model}
Trials are organized into blocks of 10, and a single transfer-function parameter set remains fixed for the duration of one block. For the first three blocks (i.e.\ the first 30 trials) of each participant, the machine-learning backend is not yet used to propose parameters; instead, each of the six parameters is independently sampled uniformly at random from its predefined bounds (Table~\ref{tab:param-bounds}). This warm-up/bootstrap phase serves two purposes: it generates an initial, sufficiently diverse set of observations for the optimization model to learn from, and it avoids relying on an uninitialized or poorly informed model at the very beginning of a session, where no data are yet available.

Only after these first three blocks have been completed does the system switch to model-based parameter generation. The optimization backend treats the problem as \emph{participant-aware} (multi-task) rather than optimizing in isolation for a single individual: whenever a new parameter set is requested, the Lambda function retrieves not only the requesting participant's own trial history but also the (anonymized) trial histories of every other participant recorded so far, and forwards all of them together to the SageMaker endpoint. There, one participant is treated as one \emph{task} in the sense of a multi-task Gaussian Process; a BoTorch \texttt{MultiTaskGP} with an intrinsic co-regionalization (ICM) kernel is fitted using the task identity as an additional input feature. This lets the model share statistical strength about the relationship between transfer-function parameters and completion time across participants, rather than fitting a separate, data-starved model per participant. Because each of the 10 fixed target positions within a block (see Section~\ref{sec:task}) can differ systematically in average completion time, one such multi-task GP is fit independently per target position, yielding 10 posterior predictive models per candidate parameter set. 100 candidate parameter sets are drawn uniformly at random from the bounded search space (plus the participant's currently active parameter set as an additional candidate), each of the 10 fitted GPs predicts its posterior mean completion time for every candidate, and the 10 resulting predictions are scalarized into a single score, $\mathrm{score} = \overline{t} + 0.35\, t_{\max} + 0.10\,(t_{\max} - t_{\min})$, where $\overline{t}$ is the mean predicted completion time across the 10 target positions, $t_{\max}$ and $t_{\min}$ are the largest and smallest predicted times, respectively. The candidate minimizing this joint objective -- which penalizes both a high average completion time and a large imbalance in performance across target positions -- is selected as the next block's parameter set. If fewer than two completed blocks of pooled training data are available for a given participant, or if model fitting fails for any reason, the backend falls back to returning the participant's current parameter set unchanged.

\paragraph{Interface elements and progress feedback.} A horizontal progress indicator above the list shows, as a row of 10 pill-shaped segments, how many of the 10 trials belonging to the currently active transfer function have already been completed. Directly above the list, a banner displays the number the participant is currently searching for. Two identical vertical location-feedback tracks are rendered on the left and right edge of the screen, each showing two markers: one fixed at the position of the current target (proportional to its index within the 330-entry list) and one continuously updated to reflect the participant's current scroll position (computed from the on-screen offset of the topmost rendered items). This lets participants continuously orient themselves relative to the target without having to keep the target itself in view while scrolling.

While a trial is in progress, the target entry is visually distinguished from all other (otherwise identically styled) entries by a red border and light red background; once the participant has tapped the correct entry, it briefly switches to a green background before the next trial begins. In addition to the timing data used by the optimizer, several gesture-level quantities are computed in real time during each trial for on-screen feedback and threshold logic purposes, including swipe direction, per-gesture distance and duration, average and maximum swipe speed, the number of direction reversals (``switchbacks''/clutches) within a trial, and whether and by how far the target was overshot. Of these, the total elapsed time until the correct entry is tapped (\texttt{timeMs}), the net scrolled distance during the trial (\texttt{scrollDistance}), and a completion timestamp are recorded and persisted to the backend per trial; these are the quantities used as the optimization objective described above.

Trial data belonging to one block are collected locally in the browser and only submitted to the backend once all 10 trials of a block are complete, at which point they are appended atomically to the participant's stored trial history together with the transfer-function parameter set that was active during that block. After a block has been submitted, the participant is shown a waiting screen until a new parameter set has been generated (either through random sampling, during the warm-up phase, or through the Gaussian-Process optimizer thereafter); the next block of trials is then only started once the participant explicitly confirms via a button click, creating a clear separation between successive optimization blocks and ensuring that a new transfer function is only introduced once the backend has produced an updated, validated parameter set.

\subsection{Task}
\label{sec:task}

Participants were asked to repeatedly locate and select a specified target entry within the 330-entry list. Ten fixed target positions were used throughout the experiment: entries $30, 60, 90, \dots, 300$, i.e.\ every 30th position starting 30 entries from the top and ending 30 entries from the bottom of the list. This excludes the first and last 30 entries from ever being used as a target, so that every target position is reachable by scrolling in either direction and no target is trivially visible without scrolling.

For each block of trials -- corresponding to one fixed transfer-function parameter set -- all 10 target positions were presented exactly once, in a randomized order that was freshly shuffled at the start of every block. Before the first randomized block, participants completed a single untimed practice trial with a fixed target (list entry 180) in order to familiarize themselves with the touch-scrolling interaction and the location-feedback display; this practice trial is not included in the recorded/optimized trial data.

During a block, the target entry was visually indicated by a red border and background while the trial was in progress (turning green briefly upon successful selection), while all other entries retained their default appearance. Location-feedback tracks on both sides of the screen additionally indicated the participant's current scroll position relative to the target position at all times. Participants proceeded through the 10 randomized targets of a block one after another, with progress tracked by the progress indicator above the list.

Once all 10 trials of a block were completed, the corresponding trial data (completion time, scrolled distance, and target position per trial) were submitted to the backend together with the transfer-function parameters used during that block, and participants waited until an updated parameter set had been generated. The next block -- using the newly generated transfer-function parameters -- could only be started by an explicit button click once the new parameters were confirmed to be available, ensuring that every block was evaluated with a single, well-defined and fully generated transfer function.
