\chapter{System Description}

\section{Overview and Design Rationale}
\label{sec:overview}

The experimental system is a web-based apparatus for studying touch-driven list scrolling under a \emph{configurable} transfer function. Its purpose is twofold: to present participants with a controlled search-and-select task on a long, continuously scrollable list, and to \emph{adapt} the scrolling dynamics to each participant over the course of a session by means of an online optimization loop. Every part of the system is defined as code and deployed automatically, so that the exact configuration used during data collection is reproducible.

The guiding architectural principle is a strict separation of concerns across three layers. A \emph{presentation} layer -- a React single-page application -- renders the list and takes full programmatic control of touch input and scrolling. A \emph{persistence} layer -- a managed GraphQL API backed by a schemaless document store -- records participants and their completed trial blocks. An \emph{optimization} layer -- a serverless machine-learning backend -- consumes the recorded data on demand and proposes the next transfer-function parameter set. Because the three layers communicate only through a small, well-defined GraphQL interface, each of them is independently deployable and version-controlled (Section~\ref{sec:architecture}).

A second, central design decision concerns the scrolling behaviour itself. Rather than relying on the browser's native momentum scrolling or on a framework's default scroll view, the post-touch (fling) motion is governed by an explicit, parameterized transfer function that was derived directly from the source code of Android's \texttt{OverScroller} class (Section~\ref{sec:transfer-function}). Exposing the constants that are otherwise fixed in that source as tunable parameters turns the qualitative ``feel'' of scrolling into a well-defined numerical search space, which the optimization layer can then adapt per participant (Section~\ref{sec:ml-model}). This coupling between a physically motivated interaction model and a data-driven optimizer is the conceptual core of the system.

\section{System Architecture}
\label{sec:architecture}

The system is event-driven from end to end: raw interaction data are recorded by the frontend, persisted in blocks of ten trials, evaluated on demand by a Gaussian-Process-based optimizer, and the resulting new transfer-function parameters are made available to the participant for the subsequent block. The following subsections describe the four building blocks of this architecture.

\subsection{Frontend}
\label{sec:frontend}

The frontend is a \textbf{React} single-page application written in plain \textbf{JavaScript}. Its static build artifacts (HTML, JavaScript, CSS) are hosted in an \textbf{Amazon S3} bucket and delivered to participants through an \textbf{Amazon CloudFront} content-delivery distribution, which also terminates HTTPS. The frontend is responsible for rendering the list, running the custom touch-input and scrolling pipeline (Section~\ref{sec:touch-pipeline}), evaluating the transfer function locally in real time (Section~\ref{sec:transfer-function}), and collecting per-trial measurements that are submitted to the backend one block at a time.

\subsection{Backend and Data Flow}
\label{sec:backend}

The application backend is built around \textbf{AWS AppSync}, a managed GraphQL API service, which exposes queries and mutations for participant management (\texttt{createParticipant}, \texttt{updateParticipant}), for storing completed trial blocks (\texttt{appendParticipantAttemptBlock}), and for requesting a new transfer-function parameter set (\texttt{triggerNextParameterSet}). \textbf{Amazon DynamoDB} serves as the persistent, schemaless data store behind this API: each participant is represented as a single item holding demographic fields (name, e-mail, birth date, smartphone ownership, daily screen time), the currently active transfer-function parameter set, the next (candidate) parameter set once available, and the complete history of completed trial blocks stored as a nested JSON (\texttt{AWSJSON}) attribute. Because a participant's entire state lives in one item, reading and appending trial data require no joins and remain a single-item operation.

\subsection{Optimization Backend}
\label{sec:opt-backend}

Rather than being triggered indirectly through DynamoDB Streams, the machine-learning backend is invoked synchronously as part of the GraphQL request flow: whenever a participant finishes a block of 10 trials, the frontend calls the \texttt{triggerNextParameterSet} mutation, whose AppSync resolver invokes an \textbf{AWS Lambda} function. This Lambda function reads the calling participant's full trial history from DynamoDB, additionally performs a table scan to collect the (anonymized) trial histories of \emph{all other} participants recorded so far, and forwards both as a single JSON payload to an \textbf{Amazon SageMaker} inference endpoint. SageMaker is configured as a \emph{serverless} endpoint (rather than an always-on instance) with a maximum concurrency of 1 and 3072\,MB of memory, so that compute resources -- and cost -- are only allocated for the brief duration of an actual invocation instead of running continuously between experimental sessions. The endpoint executes AWS's managed, prebuilt \textbf{SageMaker Scikit-learn} inference container, into which only a small custom inference script -- packaged as a \texttt{model.tar.gz} model artifact -- is injected; the Gaussian-Process optimizer itself is implemented on top of \textbf{scikit-learn} (Section~\ref{sec:ml-model} describes the model in detail). The parameter set produced by the model is returned to the Lambda function, written back into DynamoDB as the participant's \texttt{nextParameterSet}, and subsequently retrieved by the frontend once the participant confirms that they are ready to continue with the next block of trials.

\subsection{Infrastructure as Code and Deployment}
\label{sec:iac}

All infrastructure -- the S3 bucket and CloudFront distribution, the AppSync API and its resolvers, the DynamoDB table, the Lambda function, and the SageMaker endpoint -- is defined declaratively as code with \textbf{Terraform} and deployed through a \textbf{GitHub Actions} CI/CD pipeline. On every push to the main branch, the pipeline authenticates against AWS via OpenID Connect (OIDC, i.e.\ without long-lived static credentials), runs \texttt{terraform apply} to reconcile the deployed AWS infrastructure with its version-controlled definition, and then builds and publishes the React frontend. This keeps the presentation, persistence, and optimization layers independently deployable while guaranteeing that the configuration used during data collection is fully reproducible from the repository.

\section{Touch Input and Scrolling Pipeline}
\label{sec:touch-pipeline}

To obtain full and reproducible control over the scrolling dynamics, the frontend does not use the browser's native scrolling. Instead, it processes raw touch events and drives the list position programmatically, so that the fling behaviour is determined solely by the transfer function of Section~\ref{sec:transfer-function} and not by browser- or device-specific momentum implementations.

\subsection{List and Scroll Container}
\label{sec:list-container}

The user interface presents a single continuously scrollable list of $N = 330$ entries, numbered consecutively. The list is not paginated in the sense of discrete page breaks or page-navigation controls; instead, the height of each list entry is computed dynamically from the available viewport height so that exactly 15 entries are visible within the scroll container at any given time. This keeps the spatial density of the list, and therefore the visual arrangement participants perceive, consistent across devices and across trials. The list is rendered inside a dedicated scroll container whose content is not moved using the browser's native scrolling behaviour, but is instead translated vertically via a CSS \texttt{transform: translateY()} under full programmatic control of the touch-input pipeline described below.

\subsection{Gesture Processing}
\label{sec:gesture-processing}

The browser's and React's default scrolling behaviour is disabled for the list container and replaced by a custom pipeline that processes the native \texttt{onTouchStart}, \texttt{onTouchMove}, \texttt{onTouchEnd}, and \texttt{onTouchCancel} events directly. During a touch gesture, every touch-move sample is time-stamped and stored in a rolling buffer bounded by a $100$\,ms window and at most 20 samples. For real-time drag feedback the list follows the finger through an exponentially smoothed instantaneous velocity, while for launching a fling the release velocity is estimated from the buffered samples by a degree-two (quadratic) least-squares fit, taking the slope of the fitted curve at the moment of release as the launch velocity. This is more robust to jitter than a two-point derivative and, unlike a straight-line fit, follows the acceleration typically present at the end of a fling. If the estimated velocity exceeds a fixed fling threshold, it is clamped (Section~\ref{sec:param-bounds}) and passed into the fling model of Section~\ref{sec:transfer-function}; otherwise the list stops at its current position, after being clamped back into the valid scroll bounds if the participant had dragged past the list's edges.

This estimator is a faithful reimplementation of the default strategy (\texttt{lsq2}) of Android's \texttt{VelocityTracker}, the class responsible for velocity estimation in Android; the \texttt{OverScroller} itself only receives an already-computed velocity. Android rates this quadratic fit as ``very good'' and the simpler first-order variant (\texttt{lsq1}) as ``poor'', since a straight line cannot capture end-of-gesture acceleration. An estimate numerically identical to that of a physical Android device is not attainable in the browser, because the \texttt{touchmove} event stream differs from Android's \texttt{MotionEvent} pipeline in sampling rate, batching, and timestamp semantics; the fitting algorithm itself, however, reproduces Android's method exactly, so any residual discrepancy stems solely from the differing input event streams.

\subsection{Overscroll and Bounds Handling}
\label{sec:overscroll}

Scrolling is confined to the valid range spanned by the list. When a gesture or a fling would move the content beyond the top or bottom edge, overscrolling is permitted only up to a fixed maximum overscroll distance of $120$\,px and is visually compressed by a fixed resistance factor of $0.35$, so that only $35\,\%$ of the overflow is translated into visible motion. Once the touch is released in an overscrolled state, or once a fling reaches an edge, the content is returned to the nearest valid bound. This edge handling is independent of the transfer-function parameters and corresponds in spirit to the ballistic and spring-back phases of the underlying scroller model (Section~\ref{sec:ballistic-phase}).

\section{Transfer Function (Fling Model)}
\label{sec:transfer-function}

The transfer function governing post-touch (fling) motion is a physically motivated model derived directly from Android's \texttt{OverScroller} spline-deceleration algorithm. This section presents the model in full, exactly as it is defined in that source: the physical coefficient and constants, the normalized spline curve, the closed-form fling distance and duration, and the three motion phases (spline, ballistic, and cubic spring-back) that produce the motion. The derivation is self-contained and is given at the level of detail needed both to reproduce the frontend physics implementation and to understand the parameterization that constitutes the optimization search space (Section~\ref{sec:param-bounds}). Throughout, positions are measured in pixels and velocities in pixels per second, and time is measured in milliseconds unless noted otherwise.

\subsection{Fling Phase}
\label{sec:fling-phase}

The fling phase is the normal, in-bounds momentum motion that follows a flick gesture. It is built on a strict separation between the \emph{scale} of a fling -- how far and how long it travels, computed from the launch velocity and a few constants -- and its \emph{shape} -- the fixed, dimensionless temporal profile with which that distance is covered. The actual motion is then produced by normalizing distance and duration onto that fixed shape.

\subsubsection{Scale: Physical Coefficient, Fling Distance, and Duration}
\label{sec:fling-scale}

The scale converts the launch velocity $v_0$ into a total travel distance $D$ and a total duration $T$. It relies on a device-specific physical coefficient
\begin{equation}
  C \;=\; g \cdot 39.37 \cdot \mathrm{ppi} \cdot 0.84,
  \qquad
  \mathrm{ppi} \;=\; 160 \cdot \rho,
  \label{eq:sd-physical-coeff}
\end{equation}
and on a fixed dimensionless deceleration rate
\begin{equation}
  r \;=\; \frac{\ln 0.78}{\ln 0.9} \;\approx\; 2.3582 .
  \label{eq:sd-decel-rate}
\end{equation}
Given a fling friction coefficient $\mu$, the distance and the duration (the latter in milliseconds) follow in closed form as
\begin{align}
  D(v_0) &= \mu\,C \left( \frac{\beta\,\lvert v_0 \rvert}{\mu\,C} \right)^{\!\frac{r}{r-1}}, \label{eq:sd-fling-distance}\\[2pt]
  T(v_0) &= 1000 \left( \frac{\beta\,\lvert v_0 \rvert}{\mu\,C} \right)^{\!\frac{1}{r-1}}. \label{eq:sd-fling-duration}
\end{align}
The parameters are:
\begin{itemize}
  \item $v_0$, the launch velocity (px/s) estimated in Section~\ref{sec:gesture-processing}.
  \item $g = 9.80665\,\mathrm{m/s^2}$, Earth's gravitational acceleration.
  \item $\rho$, the display density, giving $\mathrm{ppi} = 160\rho$ pixels per inch, with $39.37$ the inch-per-metre conversion factor and $0.84$ a ``look and feel'' tuning constant.
  \item $C$, the resulting device-specific physical coefficient of Equation~\eqref{eq:sd-physical-coeff}.
  \item $\mu$, the dimensionless fling friction, which scales both distance and duration; in the original \texttt{OverScroller} it is the fixed constant $\mu = 0.015$ (\texttt{ViewConfiguration.SCROLL\_FRICTION}).
  \item $r \approx 2.3582$, the fixed deceleration rate of Equation~\eqref{eq:sd-decel-rate}.
  \item $\beta = 0.35$, the inflexion factor.
  \item the factor $1000$ in $T(v_0)$, converting the duration from seconds to milliseconds.
\end{itemize}
Because $\tfrac{r}{r-1} > 1$ while $\tfrac{1}{r-1} < 1$, distance grows super-linearly and duration sub-linearly with $v_0$: a faster fling covers disproportionately more ground while spreading it over a comparatively shorter time. The signed distance is $D_s = D(v_0)\,\operatorname{sgn}(v_0)$ and the target position is $x_{\text{start}} + D_s$; if this leaves the valid range it is clamped to the boundary and the duration is rescaled through the inverse normalized-time spline.

\subsubsection{Spline Curve and Normalized Sampling}
\label{sec:spline-curve}

The scale of Section~\ref{sec:fling-scale} provides the signed distance $D_s = D(v_0)\,\operatorname{sgn}(v_0)$ and the duration $T$. So that a single, fixed shape curve can describe every fling regardless of how far or how long it travels, these two quantities are \emph{normalized}: elapsed time is measured relative to $T$ and travelled distance relative to $D_s$, placing the motion in the dimensionless unit square $[0,1]\times[0,1]$. On this normalized domain the motion is a fixed position-versus-time spline $p(\tau)$ relating normalized time $\tau \in [0,1]$ to normalized distance $p \in [0,1]$. It is defined parametrically by two cubic B\'ezier curves sharing a common parameter $x \in [0,1]$; with the start and end tension constants $S = 0.5$ and $E = 1.0$ and the control ordinates
\begin{equation}
  P_1 = S\,\beta = 0.175,
  \qquad
  P_2 = 1 - E\,(1-\beta) = 0.35,
  \label{eq:sd-control-points}
\end{equation}
the normalized time and distance are
\begin{align}
  \tau(x) &= 3x(1-x)\big[(1-x)P_1 + x P_2\big] + x^3, \label{eq:sd-spline-time}\\
  p(x)    &= 3x(1-x)\big[(1-x)S + x\big] + x^3. \label{eq:sd-spline-pos}
\end{align}
This curve is sampled once, ahead of any fling and independently of $D_s$ and $T$, into a lookup table of $N+1 = 101$ entries ($N = 100$) holding $p$ at the equally spaced normalized times $\tau = i/N$.

At run time this normalization is inverted to recover pixels. At elapsed time $t$ (ms) the duration $T$ normalizes time to $\tau = t/T \in [0,1]$, which indexes the table; the two surrounding entries yield the normalized position $p(\tau)$ and its local slope $p'(\tau)$ by linear interpolation. The distance $D_s$ then scales both quantities back into pixels:
\begin{align}
  x(t) &= x_{\text{start}} + p(\tau)\,D_s, \label{eq:sd-spline-position}\\[2pt]
  v(t) &= p'(\tau)\,\frac{D_s}{T}\cdot 1000. \label{eq:sd-spline-velocity}
\end{align}

The parameters are:
\begin{itemize}
  \item $D_s$ and $T$, the signed distance and duration from Section~\ref{sec:fling-scale}: $T$ normalizes elapsed time via $\tau = t/T$, while $D_s$ scales the looked-up values back into pixels.
  \item $S = 0.5$ and $E = 1.0$, the start and end tension constants that define the shape curve.
  \item $\beta = 0.35$, the inflexion factor, which enters the control ordinates $P_1$ and $P_2$.
  \item $x$, the shared B\'ezier parameter used to trace the shape curve.
  \item $N = 100$, the number of tabulated intervals ($N+1 = 101$ samples).
  \item $\tau = t/T$, $p(\tau)$ and $p'(\tau)$, the normalized time, the tabulated position and its interpolated slope.
  \item $x_{\text{start}}$, the list position at fling launch; the factor $1000$ converts the per-millisecond velocity back to pixels per second.
\end{itemize}

\subsection{Ballistic Phase}
\label{sec:ballistic-phase}

The ballistic phase takes over when the spline motion reaches a boundary while still carrying velocity -- that is, when a fling hits the top or bottom edge of the list. It replaces the spline shape by a simple constant-deceleration (uniformly accelerated) motion that brings the content to rest, possibly after a short overshoot beyond the edge. The deceleration opposes the current motion,
\begin{equation}
  a \;=\; \begin{cases} -G, & v > 0,\\ +G, & v \le 0, \end{cases}
  \label{eq:sd-deceleration-sign}
\end{equation}
with the constant gravity value $G = 2000\,\mathrm{px/s^2}$. For a residual boundary velocity $v$ the stopping distance is $d_{\text{stop}} = v^2/(2\lvert a\rvert)$; if it exceeds the permitted overscroll distance $O$, the deceleration is increased so that the motion stops exactly at $O$,
\begin{equation}
  a \;=\; -\operatorname{sgn}(v)\,\frac{v^2}{2\,O},
  \qquad d_{\text{stop}} = O,
  \label{eq:sd-over-decel}
\end{equation}
and the phase lasts $T_{\text{ball}} = -1000\,v/a$ milliseconds. Within the phase, with $t$ in seconds, the motion is uniformly accelerated,
\begin{align}
  x(t) &= x_{\text{start}} + v\,t + \tfrac{1}{2}\,a\,t^2, \label{eq:sd-ballistic-position}\\[2pt]
  v(t) &= v + a\,t. \label{eq:sd-ballistic-velocity}
\end{align}
The parameters are: $v$, the residual velocity at the moment the boundary is reached; $a$, the signed deceleration; $G = 2000\,\mathrm{px/s^2}$, the constant background deceleration; $O$, the maximum permitted overscroll distance; $d_{\text{stop}}$, the resulting stopping distance; and $T_{\text{ball}}$, the phase duration.

\subsection{Cubic Spring-Back Phase}
\label{sec:cubic-phase}

The cubic spring-back phase returns an over-scrolled position smoothly onto the boundary, so that content released or flung past an edge eases back into the valid range instead of snapping. Over the overshoot $O$, with normalized phase time $\tau = t/T_{\text{spring}} \in [0,1]$, the displacement and velocity relative to the start of the phase are
\begin{align}
  x(t) &= x_{\text{start}} + \operatorname{sgn}(v)\,O\,\big(3\tau^2 - 2\tau^3\big), \label{eq:sd-cubic-position}\\[2pt]
  v(t) &= \operatorname{sgn}(v)\,O\,\frac{6}{T_{\text{spring}}}\big(\tau^2 - \tau\big), \label{eq:sd-cubic-velocity}
\end{align}
with the spring-back duration
\begin{equation}
  T_{\text{spring}} \;=\; 1000\,\sqrt{-2\delta/a} \quad (\mathrm{ms}).
  \label{eq:sd-spring-duration}
\end{equation}
The parameters are: $O$, the overshoot amplitude; $\delta$, the over-scroll distance still to be recovered; $a$, the deceleration from Equation~\eqref{eq:sd-deceleration-sign}; $\tau$, the normalized phase time; and $T_{\text{spring}}$, the resulting phase duration. The smooth-step polynomial $3\tau^2 - 2\tau^3$ guarantees zero relative velocity at both ends, so the motion starts and ends at rest and reaches the boundary exactly at $\tau = 1$.

\subsection{Parameterization and Search Space}
\label{sec:param-bounds}

In the original \texttt{OverScroller}, the quantities introduced above are fixed constants. To make the scrolling behaviour adaptable, six of them are exposed as tunable parameters that constitute the search space of the optimization process (Section~\ref{sec:ml-model}): the fling friction $\mu$ (\texttt{scrollFriction}); the two bases $\texttt{x1}$ and $\texttt{x2}$ that generalize the deceleration rate to $r = \ln(\texttt{x1})/\ln(\texttt{x2})$, mirroring the hard-coded $\ln 0.78/\ln 0.9$ of Equation~\eqref{eq:sd-decel-rate}; the inflexion factor $\beta$ (\texttt{inflexion}); a multiplier on the physical coefficient $C$ of Equation~\eqref{eq:sd-physical-coeff} (\texttt{physicalCoeffTuning}); and an upper bound $\texttt{maxLaunchVelocityPxMs}$ applied to the estimated launch velocity (Section~\ref{sec:gesture-processing}) before it enters the model. Each parameter is constrained to a fixed lower and upper bound (Table~\ref{tab:param-bounds}), chosen so that every generated transfer function remains physically plausible and usable; these bounds are shared verbatim between the frontend physics implementation and the optimization backend. The edge behaviour of Section~\ref{sec:overscroll} (maximum overscroll $120$\,px, resistance $0.35$) is held fixed and is not part of the search space.

\section{Adaptive Parameter Optimization}
\label{sec:ml-model}

Trials are organized into blocks of 10, and a single transfer-function parameter set remains fixed for the duration of one block. After each block, the system may propose a new parameter set for the next block, gradually adapting the scrolling behaviour to the participant.

\subsection{Warm-up and Bootstrap Phase}
\label{sec:warmup}

For the first three blocks (i.e.\ the first 30 trials) of each participant, the machine-learning backend is not yet used to propose parameters; instead, each of the six parameters is independently sampled uniformly at random from its predefined bounds (Table~\ref{tab:param-bounds}). This warm-up/bootstrap phase serves two purposes: it generates an initial, sufficiently diverse set of observations for the optimization model to learn from, and it avoids relying on an uninitialized or poorly informed model at the very beginning of a session, where no data are yet available.

\subsection{Participant-Aware Multi-Task Gaussian Process}
\label{sec:mtgp}

Only after these first three blocks have been completed does the system switch to model-based parameter generation. The optimization backend treats the problem as \emph{participant-aware} (multi-task) rather than optimizing in isolation for a single individual: whenever a new parameter set is requested, the Lambda function retrieves not only the requesting participant's own trial history but also the (anonymized) trial histories of every other participant recorded so far, and forwards all of them together to the SageMaker endpoint. There, one participant is treated as one \emph{task} in the sense of a multi-task Gaussian Process: a single scikit-learn \texttt{GaussianProcessRegressor} is fitted on the pooled data of all participants, with the integer participant/task identity appended as an additional numeric input feature alongside the six transfer-function parameters. Instead of a dedicated multi-task/co-regionalization (ICM) kernel, an anisotropic (ARD) kernel of the form $\mathrm{ConstantKernel}\times\mathrm{RBF}+\mathrm{WhiteKernel}$ is used, in which every input dimension -- including the task-identity dimension -- receives its own length scale, and whose hyperparameters are fitted by maximizing the marginal log-likelihood (L-BFGS, with two random restarts and target normalization). Letting the task-identity dimension carry its own length scale is what allows the model to learn how strongly participant-level differences should be weighted. This lets the model share statistical strength about the relationship between transfer-function parameters and completion time across participants, rather than fitting a separate, data-starved model per participant. Because each of the 10 fixed target positions within a block (see Section~\ref{sec:task}) can differ systematically in average completion time, one such multi-task GP is fit independently per target position, yielding 10 posterior predictive models per candidate parameter set.

\subsection{Candidate Scoring and Selection}
\label{sec:scoring}

100 candidate parameter sets are drawn uniformly at random from the bounded search space (plus the participant's currently active parameter set as an additional candidate), each of the 10 fitted GPs predicts its posterior mean completion time for every candidate, and the 10 resulting predictions are scalarized into a single score, $\mathrm{score} = \overline{t} + 0.35\, t_{\max} + 0.10\,(t_{\max} - t_{\min})$, where $\overline{t}$ is the mean predicted completion time across the 10 target positions, and $t_{\max}$ and $t_{\min}$ are the largest and smallest predicted times, respectively. The candidate minimizing this joint objective -- which penalizes both a high average completion time and a large imbalance in performance across target positions -- is selected as the next block's parameter set. If fewer than two completed blocks of pooled training data are available for a given participant, or if model fitting fails for any reason, the backend falls back to returning the participant's current parameter set unchanged.

\subsection{SageMaker Inference Implementation and Deployment}
\label{sec:sagemaker}

The optimization model is not persisted as a trained artifact; instead, a fresh Gaussian Process is refitted from scratch on every invocation, directly from the trial data contained in the request payload, which keeps the deployment stateless and always consistent with the most recent data. Concretely, the inference logic is implemented as a single Python module exposing the four handler functions expected by the SageMaker inference toolkit (\texttt{model\_fn}, \texttt{input\_fn}, \texttt{predict\_fn}, \texttt{output\_fn}): \texttt{model\_fn} performs no model loading and returns an empty model, while the GP fitting and candidate scoring described above are carried out entirely within \texttt{predict\_fn}. This module is packaged, together with an (empty) requirements file, into a gzip-compressed \texttt{model.tar.gz} archive following SageMaker's \texttt{code/} script-mode layout, uploaded to S3 by Terraform, and loaded into the prebuilt Scikit-learn container at container start via the \texttt{SAGEMAKER\_PROGRAM} and \texttt{SAGEMAKER\_SUBMIT\_DIRECTORY} environment variables. Because the model artifact contains only source code and no learned weights, and because scikit-learn and NumPy are already present in the prebuilt container, no additional Python dependencies have to be installed at cold start. Requests and responses are exchanged as \texttt{application/json}: the request carries the current parameter set and the pooled per-participant trial histories, and the response carries the newly proposed parameter set together with lightweight metadata (the selection strategy that was actually used and the number of pooled observations the decision was based on).

\section{Experimental Procedure}
\label{sec:procedure}

\subsection{Task Design}
\label{sec:task}

Participants were asked to repeatedly locate and select a specified target entry within the 330-entry list. Ten fixed target positions were used throughout the experiment: entries $30, 60, 90, \dots, 300$, i.e.\ every 30th position starting 30 entries from the top and ending 30 entries from the bottom of the list. This excludes the first and last 30 entries from ever being used as a target, so that every target position is reachable by scrolling in either direction and no target is trivially visible without scrolling.

For each block of trials -- corresponding to one fixed transfer-function parameter set -- all 10 target positions were presented exactly once, in a randomized order that was freshly shuffled at the start of every block. Before the first randomized block, participants completed a single untimed practice trial with a fixed target (list entry 180) in order to familiarize themselves with the touch-scrolling interaction and the location-feedback display; this practice trial is not included in the recorded/optimized trial data.

\subsection{Interface Elements and Progress Feedback}
\label{sec:interface}

A horizontal progress indicator above the list shows, as a row of 10 pill-shaped segments, how many of the 10 trials belonging to the currently active transfer function have already been completed. Directly above the list, a banner displays the number the participant is currently searching for. Two identical vertical location-feedback tracks are rendered on the left and right edge of the screen, each showing two markers: one fixed at the position of the current target (proportional to its index within the 330-entry list) and one continuously updated to reflect the participant's current scroll position (computed from the on-screen offset of the topmost rendered items). This lets participants continuously orient themselves relative to the target without having to keep the target itself in view while scrolling. While a trial is in progress, the target entry is visually distinguished from all other (otherwise identically styled) entries by a red border and light red background; once the participant has tapped the correct entry, it briefly switches to a green background before the next trial begins.

\subsection{Data Collection and Recorded Metrics}
\label{sec:data-collection}

In addition to the timing data used by the optimizer, several gesture-level quantities are computed in real time during each trial for on-screen feedback and threshold-logic purposes, including swipe direction, per-gesture distance and duration, average and maximum swipe speed, the number of direction reversals (``switchbacks''/clutches) within a trial, and whether and by how far the target was overshot. Of these, the total elapsed time until the correct entry is tapped (\texttt{timeMs}), the net scrolled distance during the trial (\texttt{scrollDistance}), and a completion timestamp are recorded and persisted to the backend per trial; these are the quantities used as the optimization objective described above.

Trial data belonging to one block are collected locally in the browser and only submitted to the backend once all 10 trials of a block are complete, at which point they are appended atomically to the participant's stored trial history together with the transfer-function parameter set that was active during that block. After a block has been submitted, the participant is shown a waiting screen until a new parameter set has been generated (either through random sampling during the warm-up phase, or through the Gaussian-Process optimizer thereafter); the next block of trials is then only started once the participant explicitly confirms via a button click, creating a clear separation between successive optimization blocks and ensuring that a new transfer function is only introduced once the backend has produced an updated, validated parameter set.
